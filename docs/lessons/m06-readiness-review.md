# 目标项目就绪评审

<p class="lesson-deck">不要用“代码写完了”判断是否就绪；现场解释控制权，改一处边界，再用测试和真实运行证明结果。</p>

## 学习结果

学完本章后，你应该能够：

- 在 15 分钟内解释上层调用、进程入口、`Runner`、模型、工具和结构化返回之间的数据流；
- 指出每一层能控制什么，不能替下一层判断什么；
- 说明无效请求、资料缺失、工具失败、工具超时、turn 上限、运行超时和无效最终输出由哪一层首先识别；
- 现场增加一个从已有只读数据得到的字段，并补齐 schema、确定性测试和进程级断言；
- 列出通用 worker 接入目标项目时必须替换的边界，以及必须保留的安全约束；
- 用默认自动检查证明改动没有破坏已有路径；
- 用公开合成资料完成一次真实模型 smoke run，并用 `trace_id` 复查运行；
- 区分“可以开始目标功能开发”和“已经生产就绪”。

!!! abstract "本章边界"

    M06 是能力评审，不是新的架构章节，也不是生产上线审批。它不引入 session、handoff、
    写工具、通用多 Agent 框架或新的服务依赖。评审时只改一个小字段或一个只读工具，不重构
    M05 worker。

## 核心内容

### 1. 四项证据必须同时通过

“看懂了”不能证明你能独立修改 worker。本章只接受四项可以复查的证据：

| 门槛 | 要做什么 | 通过信号 |
| --- | --- | --- |
| 讲解 | 15 分钟内从输入讲到输出，并解释失败归属 | 不看教材也能说清数据、控制权和停止点 |
| 小改动 | 增加一个只读字段或工具，并补测试 | schema、结果和进程协议同步变化，权限没有扩大 |
| 自动检查 | 运行类型检查、静态检查和默认测试 | 所有命令退出码为 `0`，默认测试不调用真实模型 |
| 真实运行 | 用公开合成资料运行一次完整路径 | 得到符合 schema 的 JSON，并能按 `trace_id` 找到运行 |

四项必须在同一个最终版本上通过。先跑 smoke run，之后又修改代码，不能把改动前的运行当作
最终证据。某一项失败时，记录失败点并回到对应章节；不要把部分通过写成“就绪”。

### 2. 先讲清数据怎样移动，再讲 SDK 名称

15 分钟讲解的主线只有一条：

```text
上层程序准备一个 TaskRequest JSON
  → 进程入口读取并校验
  → 应用构造模型输入和本地 WorkerContext
  → Runner 推进模型与只读工具之间的循环
  → SDK 生成并校验结构化最终输出
  → 应用检查资料覆盖和状态约束
  → 进程写出一个 WorkerResult JSON 与对应退出码
  → 上层程序决定使用结果、重试还是停止
```

讲解每一步时都回答三个问题：谁读取数据，谁可以改变控制流，谁检查结果。下面的表格给出
最低要求：

| 层 | 读取什么 | 控制什么 | 交给下一层什么 |
| --- | --- | --- | --- |
| 上层程序 | 请求与 JSON Schema | 是否启动、重试或停止 | 一个请求对象 |
| 进程入口 | 标准输入或 UTF-8 文件 | 输入是否合法，标准流和退出码 | 已校验的 `TaskRequest` |
| 应用包装层 | 请求、本地依赖、运行配置 | prompt、工具清单、timeout、状态约束 | 模型输入、`WorkerContext`、`RunConfig` |
| `Runner` | 起始 Agent 和输入 | 模型/工具循环、turn 计数和停止 | `RunResult` 或 SDK 异常 |
| 只读工具 | 经过约束的参数与本地 context | 只读访问、allowlist、单次 timeout | 结果或明确失败 |
| 应用包装层 | `final_output`、异常和资料覆盖 | 稳定状态、错误代码、最小记录 | 合法的 `WorkerResult` |
| 上层程序 | JSON、状态、错误和退出码 | 后续业务动作 | 不进入 worker 的内部循环 |

`Runner` 推进循环，不拥有资料权限、凭据、持久状态或领域完成标准。`output_type` 让最终输出
经过 schema 校验，但不能证明请求的资料已经全部读取。能把这两点说清，说明你没有把 SDK
能力和应用责任混在一起。

### 3. 对每种失败，分别说出“发现”和“对外表示”

一次失败常经过两层：靠近原因的组件先发现问题，应用包装层再把它变成稳定的
`WorkerResult`。评审时不要只背错误代码，要说明两个动作。

| 场景 | 首先识别的层 | 应用怎样对外表示 |
| --- | --- | --- |
| JSON 无效或字段类型错误 | 进程入口的 `TaskRequest.model_validate_json(...)` | `failed`、`INVALID_REQUEST`、退出码 `1` |
| 路径越过允许根目录或参数不在 allowlist | 只读工具的普通代码 | 映射为稳定工具错误；不访问目标资源 |
| 请求的资料不存在 | 资料工具先报告缺失，包装层再检查覆盖 | 有可信部分结果时为 `incomplete`、`SOURCE_MISSING`、退出码 `2` |
| 只读查询失败 | 查询工具或客户端 | `failed`、`TOOL_FAILURE`、退出码 `1` |
| 单次工具调用超时 | 工具 timeout 边界 | `failed`、`TOOL_TIMEOUT`、退出码 `1` |
| 超过 `max_turns` | `Runner` 到达 turn 上限 | `incomplete`、`MAX_TURNS`、退出码 `2` |
| 整次运行超过 20 秒 | 应用的运行级 timeout | `failed`、`RUN_TIMEOUT`、退出码 `1` |
| 最终输出不符合结构或运行时类型 | SDK 的输出解析或 `final_output_as(...)` 检查 | `failed`、`INVALID_FINAL_OUTPUT`、退出码 `1` |
| 结构合法但资料覆盖不足 | 应用的确定性领域检查 | `incomplete` 和对应稳定错误，退出码 `2` |

错误字符串、堆栈和原始输入可能含调用方数据。包装层记录固定事件名、`trace_id`、状态和错误
代码即可。上层程序读取 JSON 决定后续动作，不应解析日志猜测任务状态。

### 4. 现场改动要穿过真实边界，但保持很小

优先增加一个从已有只读数据得到的输出字段，例如证据种类。它比新增服务客户端更适合现场
评审：仍然能检查契约、数据传递、序列化和测试，却不会扩大权限或引入网络故障。

改动按下面的顺序完成：

1. 先写失败测试，说明新字段应出现在结果 schema、序列化 JSON 和进程级成功场景中；
2. 在负责这份数据的 Pydantic 模型中增加字段，并规定它是否必填；
3. 从现有只读工具结果或本地确定性代码填入字段，不从凭据、logger 或私有路径推断；
4. 只有模型必须生成这个字段时才修改 Agent 指令；能由普通代码确定时，不增加模型工作；
5. 补齐无效值、序列化往返和进程输出断言；
6. 运行全部默认检查，再运行真实 smoke run。

如果选择新增只读工具，仍只做一件事：定义窄参数、使用本地 `WorkerContext` 中已有的只读
依赖、设置单次 timeout，并直接测试成功、越界和底层失败。不要在 45 分钟评审中同时加入新
客户端、缓存、重试框架或写操作。

!!! tip "怎样判断改动足够小"

    改动应能在 15 分钟左右完成，并能在剩余时间里跑完测试和讲清影响。如果必须重写结果
    契约或进程入口，说明选择的改动太大，或者 M05 的边界还没有稳定。

### 5. 接入目标项目时，明确哪些要替换、哪些必须保留

通用 worker 不能靠改几个环境变量就自动适配目标项目。先写边界清单，再逐项找目标项目的
实际拥有者。清单不要记录公司名称、私有地址、真实凭据或私有资料内容。

| 边界 | 接入时要替换或确认 | 必须保留的约束 |
| --- | --- | --- |
| 调用方式 | 子进程、任务队列或进程内调用；请求由谁创建 | 一次调用的输入、输出和 timeout 清楚可测 |
| `TaskRequest` | 目标任务标识、问题和资料引用 | 调用前校验；请求不能注入本地依赖 |
| `WorkerResult` | 下游真正需要的答案、证据和错误字段 | 状态约束稳定；下游不解析自由文本判断完成 |
| 资料工具 | 目标资料位置、身份和访问接口 | 默认拒绝；只读；路径或标识使用 allowlist |
| 查询工具 | 目标只读客户端和允许的查询参数 | 单次 timeout；异常不伪装成正常数据 |
| 模型配置 | 明确模型、供应商配置和凭据来源 | 凭据留在本地 context 或环境，不进入 prompt |
| 运行预算 | 目标系统允许的 turn 数和总时限 | `max_turns` 与运行级 timeout 都存在 |
| 错误映射 | 目标项目要识别的稳定错误代码 | 原因、状态和退出行为保持一致且可断言 |
| tracing | workflow 名、关联标识和导出位置 | 关闭敏感输入与工具内容；`trace_id` 可关联 |
| 最小记录 | 保存位置、保留时间和访问权限 | 不保存 prompt、完整答案、工具原始输出或异常文本 |
| 测试边界 | 目标项目怎样注入假 runner 和假只读客户端 | 默认测试没有真实模型或真实服务调用 |
| 重试责任 | 上层程序在什么错误后重试 | worker 不自行隐藏失败；重复调用仍有成本和审计记录 |

“必须保留”不是要求目标项目沿用相同文件名。它要求目标实现继续满足相同的可观察行为和安全
边界。

### 6. 15 分钟讲解有固定时间盒

让另一位工程师计时并随时追问。按下面的顺序讲，合计正好 15 分钟：

1. 2 分钟：展示请求和结果 schema，以及三个状态和退出码；
2. 4 分钟：沿一条成功路径说明数据和控制权；
3. 3 分钟：选择三个不同层的失败，说明谁发现、谁映射、调用方怎样处理；
4. 2 分钟：展示脱敏 trace 和最小记录各自保存什么；
5. 2 分钟：展示假 runner 的确定性测试与真实 smoke run 分别证明什么；
6. 2 分钟：展示目标项目边界清单，并指出第一个要替换的接口。

评审者可以改变一个条件，例如“资料存在，但查询超时”。你应沿现有路径说明结果，不应临时
发明新的状态或重试规则。

### 7. 自动检查和真实运行提供不同证据

先运行默认检查：

```bash
uv run ruff check .
uv run pyright
uv run pytest
```

这些命令应覆盖普通代码、类型边界、schema、状态约束和进程协议，并且不发出真实模型请求。
然后显式配置模型和凭据，只用公开合成资料运行一次：

```bash
uv run python -m evidence_worker.cli fixtures/requests/complete.json
```

验证标准输出只有一个 `WorkerResult` JSON，状态为 `completed`，退出码为 `0`。再用最小记录
中的 `trace_id` 检查模型轮次、只读工具顺序和敏感内容设置。不要把 API key、原始 prompt、
工具输出或私有资料复制到评审记录。

默认测试证明已列出的场景在可控输入下稳定。一次真实运行只证明当前模型、配置、工具和进程
入口连接成功一次。两者都通过，仍不等于容量、长期可靠性、安全审计或生产部署已经完成。

### 8. 失败时只回到暴露问题的章节

| 没通过的证据 | 回到哪里 |
| --- | --- |
| 说不清模型输入与本地 context | M01 |
| 不能证明工具只读、路径受限或 timeout 生效 | M02 |
| 状态、错误或停止条件互相矛盾 | M03 |
| 默认测试会联网，或 trace 与记录含敏感内容 | M04 |
| JSON、标准流、退出码或端到端路径不稳定 | M05 |

修正后重新执行四项门槛。只有讲解、小改动、自动检查和最终版本的真实 smoke run 都通过，才
记录“具备开始目标功能开发的能力”。这个结论只表示可以开始接入，不表示 worker 已经生产
就绪。

## 习题

先完成问题，再展开参考答案。

### 概念与代码阅读

1. 为什么已有完整代码和一次成功运行仍不足以通过 M06？
2. `Runner` 控制什么，应用代码仍控制什么？
3. 为什么失败评审要分别说明“首先识别的层”和“对外表示的层”？
4. 资料工具报告缺失后，为什么还要由应用包装层检查覆盖并决定 `incomplete`？
5. 为什么现场改动优先选择从已有只读数据得到的字段？
6. 如果新字段能由普通代码确定，为什么不应让模型生成它？
7. 目标项目可以更换进程调用方式吗？什么约束仍必须保留？
8. 默认自动测试和一次真实 smoke run 分别证明什么？
9. 判断正误：四项门槛通过后，worker 就已经生产就绪。
10. 如果最后一次 smoke run 后又修改了结果模型，是否还能使用原来的 smoke run 作为最终证据？

<details class="exercise-answers">
<summary>参考答案</summary>

1. M06 还要求学习者能独立解释控制权、现场完成一处小改动、让自动检查通过，并在同一最终
   版本上完成真实运行。现成代码可能是照着写出的，单次成功也没有覆盖失败路径。
2. `Runner` 推进模型与工具循环并执行 turn 上限。应用仍控制工具实现与权限、输入校验、
   timeout、领域状态、记录和对外协议。
3. 靠近原因的组件最适合发现具体问题，应用包装层则负责把不同异常稳定地交给调用方。混在
   一起会让错误被隐藏，或让上层依赖 SDK 内部异常。
4. 工具只能说明某次读取失败。包装层知道请求要求哪些资料、已有结果是否可信，因此由它决定
   整个任务是否不完整。
5. 这种改动能穿过模型、schema、序列化和测试边界，又不需要扩大权限或接入新的服务。
6. 普通代码能确定的值更稳定、更容易测试，也不消耗模型调用去猜一个已有事实。
7. 可以。目标项目可以改用队列或进程内调用，但输入输出契约、校验、timeout、状态和可测试
   行为仍要清楚。
8. 默认测试证明列出的场景在可控输入下重复得到同样结果且不会联网。真实 smoke run 证明
   当前模型、配置、工具和入口至少成功连接一次。
9. 错。通过只表示具备开始目标功能开发的能力；容量、长期可靠性、安全审计和部署仍需另行
   验证。
10. 不能。结果模型改动可能改变输出和序列化；必须在最终版本上重新运行 smoke test。

### 实战：完成一次目标项目就绪评审

在 M05 完成的同一个 worker 上完成以下任务。不要复制新 worker，也不要在本章引入新的 Agent
架构。

1. 请另一位工程师计时，用 15 分钟讲完成功路径、三个不同层的失败、脱敏观测、两类测试和
   第一个接入边界；
2. 让评审者改变一个失败条件，现场说明结果状态、稳定错误和退出码；
3. 选择一个从已有只读数据得到的小字段，先补失败测试，再修改模型、数据传递、schema 和
   进程级断言；如果选择工具，则只增加一个窄的只读工具，并直接测试三条工具路径；
4. 写出目标项目的边界清单，至少覆盖调用方式、请求、结果、资料工具、查询工具、模型配置、
   运行预算、错误映射、tracing、最小记录、测试边界和重试责任；
5. 运行 `uv run ruff check .`、`uv run pyright` 和 `uv run pytest`；
6. 显式配置模型，用公开合成资料运行一次 `uv run python -m evidence_worker.cli
   fixtures/requests/complete.json`；
7. 校验一个 JSON、`completed`、退出码 `0`，再用 `trace_id` 检查模型轮次、工具调用和敏感
   内容设置；
8. 记录四项门槛各自的证据和未决问题，不记录密钥、私有名称、真实地址或原始资料。

完成标准：

- 15 分钟讲解不依赖教材，能逐层说明数据、控制权、停止点和失败归属；
- 一个小改动贯穿契约、实现、schema 和确定性测试，没有扩大读权限；
- 目标项目边界清单写明每项由谁替换，以及哪些约束必须保留；
- 三项默认检查都通过且没有真实模型调用；
- 最终版本的真实 smoke run 使用公开合成资料，返回一个 `completed` JSON 和退出码 `0`；
- trace 和最小记录足以复查运行，但没有密钥、原始私有数据或工具原始输出；
- 能明确说出仍未验证的生产问题，不把“可以开始开发”写成“已经生产就绪”。

本章不提供现场改动或边界清单的完整答案。评审的目的就是确认你能在没有现成实现的情况下，
把一个小需求安全地接入已有路径，并解释证据为什么足够。
